# Scope Tiers

The Solution Scope Tier determines how much of the Document Template applies, how many solution options are compared, and how deep the diagram set goes. Confirm the tier in Phase 1 using the Scope Signal answer from Discovery Checklists, and look up this file before drafting the Document Template or Diagram Templates.

## Tier Definitions

| Tier                  | Typical Scope                                                                                                                               | Example                                                            | Solution Options Required                                                               | Diagram Depth                                                                                                                               | ADR Expectation                                           |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| **Feature / Service** | A single feature or service added to, or carved out of, an existing application; narrow integration surface; no new infrastructure platform | Adding a notification service to an existing e-commerce app        | 1-2 options; a single recommended approach with a brief alternative noted is acceptable | Context + Component + Sequence diagrams; Deployment diagram only if new infrastructure is introduced                                        | 2-4 ADRs covering the most consequential decisions        |
| **Application**       | A new or significantly re-architected application; multiple integrations; a full deployment topology                                        | Building a new customer self-service portal                        | 2-3 options, scored                                                                     | Full set: Context, Component, Sequence, Integration, Data Flow, Deployment; Network diagram if the application introduces new network zones | 4-8 ADRs                                                  |
| **Program**           | A coordinated set of applications/systems delivered across phases; complex integration mesh; phased rollout                                 | A multi-year core banking platform replacement delivered in phases | 3+ options, scored                                                                      | Full set plus Network diagram and a Roadmap/Timeline diagram spanning all phases                                                            | 6+ ADRs, including cross-application sequencing decisions |

## Rules

- Always record whether enterprise standards or platform mandates exist (Discovery Checklists, Phase 1). When they do, treat them as binding constraints regardless of tier. When they do not, proceed using industry-standard practice and record the absence as an Assumption.
- Do not include a Network Architecture section or diagram for the Feature/Service tier unless the initiative introduces a new network zone or connectivity requirement.
- Do not include Disaster Recovery & Resilience as a required section for the Feature/Service tier unless a non-functional requirement explicitly demands it; include it as required for Application and Program tiers.
- Only the Program tier requires the Migration & Rollout Plan section to include a Roadmap/Timeline diagram; Feature/Service and Application tiers include a migration/rollout narrative without the roadmap diagram unless a phased delivery was confirmed in discovery.
- Sizing effort, cost, and risk narrative depth all scale with tier, but every tier still requires a fully populated Non-Functional Validation section (Document Template) — validation is never optional, only its supporting diagram set changes.
